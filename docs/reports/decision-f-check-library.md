# Decision F: Bulk Library Read for check --library

## Purpose and Status

This report records the implementation of Decision F of the [M11 plan](../m11-plan.md), authorized under Decision 47 on October 20, 2026, after M11 was integrated into `main` through pull request #15 (merge commit `9821e68`) and main-branch CI run 39381993147 passed both jobs on that commit (measured). The work is on the local branch `decision-f-check-library`, created from `9821e68`. It is not pushed, not merged, and not released. The implementation and synthetic tests were delegated to a subagent under a written design brief; the coordinating agent fixed the design, reviewed the diff, made two small corrections, and ran the verification.

## Change

`check --library` was the only caller of `MusicLibrary.allTracks()`, whose system implementation, `MusicApp.allTracks()`, sends one Apple Event plus 16 per track. Commit `3dbaba3` makes that implementation call `MusicApp.allTracksPreferringBulk()`, which runs the bulk script that `rebuild prepare` already uses and returns its tracks only when the script succeeds and its output assembles consistently: the expected sections, equal item counts, and equal first and last persistent-ID lists. In every other case, including a thrown error, the bulk-unavailable marker, an inconsistent output, or a parse error, it returns the result of the original per-track reader, and it never alters an error of that reader. The command's errors are therefore those of the original reader by construction. The bulk output is converted through the per-track parser, so the field semantics are shared. `CheckCommand.swift`, the bulk script, the per-track reader, `librarySnapshot()`, and every other command are unchanged. The findings of `check` are sorted before output, so the order of tracks cannot affect it (established by reading the source).

## Evidence

Pure tests of the selection function show that a consistent bulk output for twelve varied records and for an empty library equals the per-track parse without calling the per-track reader; that a thrown error, the unavailable marker, too few or too many sections, item-count and identifier-order mismatches, an empty output, and unparseable text each select the per-track result; and that when both readers fail the per-track error is thrown (measured). Command-level tests build one synthetic Music state of twelve registrations over the synthetic library and render it in both reader formats. Under the original and the optimized readers, `check --library` and `check PATH --library` produce identical exit status, standard output, and standard error, with findings asserted for a missing file, a registration without a file, a duplicate registration, a file not in the library, `.mp3` and `.aiff` locations that produce the other-formats note, the cloud statuses matched, subscription, uploaded, empty, and an unrecognized value, empty and non-numeric properties, and a tag difference (measured). The same identity holds when the bulk read fails and the fallback is used, and when both readers fail. These tests send no Apple Event and compare parsed text, not Music's actual output.

The prerequisite was established by the M11 version 2 qualification, which measured live field-level equivalence of the bulk and per-track readers for 12 synthetic tracks without fallback ([M11 Qualification Results, Version 2](m11-qualification-v2-results.md)). That measurement does not qualify the changed command: its live output, its behavior on larger or real libraries, the frequency of fallback, and its speed are unknown until observed.

## Verification

At `3dbaba3`, on macOS 27.0.1 (arm64) with Apple Swift 6.4, the release build succeeded, `swift format lint --strict` reported no findings, `scripts/test.sh` passed 391 Swift tests in eight runs, the packaging (12), validation and collector (176), and response-format hook (85) Python suites passed, and the package build and verification with temporary installations passed (measured). The new command-level tests and the added test dependency of `ilibraryTests` on `LibraryMac` are confined to macOS; the Linux build is inferred to be unaffected and is verified only by CI after a push.

## Proposed Maintainer Verification

The following procedure is proposed and has not been performed; it requires the maintainer's authorization and a prepared bundle. In the separate test user, without an Apple Account and with iCloud Music Library off, a new synthetic library is created and populated with original synthetic albums by the released `add` command; no qualification library, bundle, workspace, or backup folder is reused, and no personal file, external drive, or Time Machine operation is involved. The `ilibrary` executable built from `9821e68` and the one built from the Decision F commit then each run `check --library` and `check PATH --library` read-only against that library, recording exit status, standard output, standard error, and elapsed time, with Music in the same state for each pair. The outputs must be byte-identical; a difference stops the verification. Optionally, the same comparison is repeated after a deliberate tag difference and a deleted registration file in the synthetic library. The report is collected with the existing redaction rules, and acceptance of the live behavior remains the maintainer's decision.
