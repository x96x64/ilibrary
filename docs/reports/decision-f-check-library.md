# Decision F: Bulk Library Read for check --library

## Purpose and Status

This report records the implementation of Decision F of the [M11 plan](../m11-plan.md), authorized under Decision 47 on October 20, 2026, after M11 was integrated into `main` through pull request #15 (merge commit `9821e68`) and main-branch CI run 39381993147 passed both jobs on that commit (measured). The work is on the branch `decision-f-check-library`, created from `9821e68`. It was not pushed, merged, or released when this report was first written; the branch has since been published as pull request #16, which remains unmerged, and nothing is released. The implementation and synthetic tests were delegated to a subagent under a written design brief; the coordinating agent fixed the design, reviewed the diff, made two small corrections, and ran the verification.

## Change

`check --library` was the only caller of `MusicLibrary.allTracks()`, whose system implementation, `MusicApp.allTracks()`, sends one Apple Event plus 16 per track. Commit `3dbaba3` makes that implementation call `MusicApp.allTracksPreferringBulk()`, which runs the bulk script that `rebuild prepare` already uses and returns its tracks only when the script succeeds and its output assembles consistently: the expected sections, equal item counts, and equal first and last persistent-ID lists. In every other case, including a thrown error, the bulk-unavailable marker, an inconsistent output, or a parse error, it returns the result of the original per-track reader, and it never alters an error of that reader. Every error that the command reports therefore comes from the original per-track reader, and every failure of the bulk read leads to the original outcome. The converse does not hold: when the bulk read succeeds where the per-track read would have failed, for example because the per-track read of a large library exceeds its 300-second timeout or because an individual property read fails for one track, the changed command returns tracks where the original command reported an error. Whether Music produces such cases for file tracks, and how often, is unmeasured. The bulk output is converted through the per-track parser, so the field semantics are shared. `CheckCommand.swift`, the bulk script, the per-track reader, `librarySnapshot()`, and every other command are unchanged. The findings of `check` are sorted before output, so the order of tracks cannot affect it (established by reading the source).

## Evidence

Pure tests of the selection function show that a consistent bulk output for twelve varied records and for an empty library equals the per-track parse without calling the per-track reader; that a thrown error, the unavailable marker, too few or too many sections, item-count and identifier-order mismatches, an empty output, and unparseable text each select the per-track result; and that when both readers fail the per-track error is thrown (measured). Command-level tests build one synthetic Music state of twelve registrations over the synthetic library and render it in both reader formats. Under the original and the optimized readers, `check --library` and `check PATH --library` produce identical exit status, standard output, and standard error, with findings asserted for a missing file, a registration without a file, a duplicate registration, a file not in the library, `.mp3` and `.aiff` locations that produce the other-formats note, the cloud statuses matched, subscription, uploaded, empty, and an unrecognized value, empty and non-numeric properties, and a tag difference (measured). The same identity holds when the bulk read fails and the fallback is used, and when both readers fail. Because the two readers return equal track arrays in these tests, the command-level comparison adds little evidence beyond that equality, and the fallback comparison is tautological by design; the selection tests carry the evidence that the bulk path is actually taken. The column order of the test fixtures is written independently of the bulk script, so only the M11 live comparison of the unchanged script ties the script's section order to the assembly. These tests send no Apple Event and compare parsed text, not Music's actual output.

The prerequisite was established by the M11 version 2 qualification, which measured live field-level equivalence of the bulk and per-track readers for 12 synthetic tracks without fallback ([M11 Qualification Results, Version 2](m11-qualification-v2-results.md)), all of whose cloud statuses were `unknown`. The bulk reader coerces cloud statuses to text outside the `tell` block, whereas the per-track reader does so inside it; the text produced for other statuses, such as matched or subscription, is unmeasured, so a difference there could change or remove the cloud-status findings of `check --library` without being detected by the synthetic tests (an unverified possibility, not a demonstrated defect). That measurement does not qualify the changed command: its live output, its behavior on larger or real libraries, the frequency of fallback, and its speed are unknown until observed.

## Cloud-Status Guard

Under Decision 48 the maintainer accepted the recommendation to restrict the bulk path before the live comparison. Commit `360dfde` makes the selection function accept a structurally consistent and parsed bulk result only when every track's cloud status text is exactly `unknown`, byte for byte; an empty library is accepted. Any other status, including `matched`, `subscription`, `uploaded`, an empty value, a differently cased or padded `unknown`, or a mixture, selects the original per-track reader, whose result or error is returned unchanged. The guard is local to `allTracksPreferringBulk`; the bulk script, the per-track reader, `librarySnapshot()`, `rebuild prepare`, and every other consumer are unchanged. It examines only the parsed text and does not prove that Music's underlying status is represented correctly, and libraries with other statuses keep the per-track reader and its speed.

The guard's tests show that bulk results whose statuses are all `unknown`, an empty library, and a single track are accepted without invoking the per-track reader; that each of nine non-matching status texts at three positions, a mixed library, and a single `matched` track select the per-track reader exactly once; that structural and parsing failures still select it exactly once; and that its errors propagate unchanged (measured). With the guard condition temporarily removed, the rejection and propagation tests failed with 58 issues and the mixed-status command tests failed their single-call assertions, while the positive tests still passed (measured by the implementing subagent and reviewed by the coordinating agent). A new command-level test with every status `unknown` shows that the bulk path is taken without a per-track call and that `check --library` and `check PATH --library` produce identical results under both readers; the earlier mixed-status command tests now also assert that their fallback was used exactly once (measured).

The evidence is therefore of four kinds, which must not be conflated: the M11 live comparison of the two readers for 12 synthetic tracks with status `unknown` (measured live); the Decision F synthetic equivalence tests of the command under both readers (measured, no Apple Event); the guard tests above (measured, no Apple Event); and the pending maintainer comparison of the changed command (not performed).

## Proposed Maintainer Verification

The complete procedure is now [Decision F Live Comparison of check --library](../decision-f-live-comparison.md), with its scripts under `scripts/validation/`; the summary below is the original proposal. The following procedure is proposed and has not been performed; it requires the maintainer's authorization and a prepared bundle. In the separate test user, without an Apple Account and with iCloud Music Library off, a new synthetic library is created and populated with original synthetic albums by the released `add` command; no qualification library, bundle, workspace, or backup folder is reused, and no personal file, external drive, or Time Machine operation is involved. The `ilibrary` executable built from `9821e68` and the one built from the Decision F commit then each run `check --library` and `check PATH --library` read-only against that library, recording exit status, standard output, standard error, and elapsed time, with Music in the same state for each pair. The outputs must be byte-identical; a difference stops the verification. Optionally, the same comparison is repeated after a deliberate tag difference and a deleted registration file in the synthetic library. The report is collected with the existing redaction rules, and acceptance of the live behavior remains the maintainer's decision. Because the test user has no Apple Account and iCloud Music Library is off, Music can be expected to report only `unknown` (inferred from the M11 observation), so this comparison cannot exercise the coercion of other cloud statuses; that limitation remains until a separately authorized observation with such statuses or a design decision that restricts the bulk path to the measured statuses.

## Corrections After Independent Review

An independent Claude review of `fa3f911` found no demonstrated or blocking defect and identified two documentation inaccuracies, which this report, the roadmap, the handoff, the changelog, and the header comment of `Sources/LibraryMac/MusicBulk.swift` now correct: the statement that the command's errors remain those of the original reader by construction, which holds only for the errors reported and not for cases in which the bulk read succeeds where the per-track read would fail, and the omitted caveat that live equivalence was observed only for the cloud status `unknown`. The message of commit `3dbaba3` states that errors stay those of the original reader and is subject to the same qualification; it is not rewritten. A stale test comment that counted ten registrations instead of twelve was also corrected.
