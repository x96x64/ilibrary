# Decision F Live Comparison Results

## Purpose and Status

This report records the maintainer-operated live comparison of `ilibrary check --library` and `ilibrary check PATH --library` between the M11 merge and the Decision F candidate, performed on October 20, 2026, with the procedure [Decision F Live Comparison of check --library](../decision-f-live-comparison.md) and its v4 bundle, and the maintainer's limited acceptance of the result under Decision 49. Only the unchanged-library phase was authorized and performed; the optional removal phase was not run. The comparison was performed by the maintainer in the separate macOS test user. No agent operated Music, the test user, or its library.

## Sources and Environment

The reference executable was built from `9821e686d169b7aee2448ceecf1f9cbe8654026f`, the merge of M11 into `main`, and the candidate from `e0f87bf2c2ae5cf8eae4924f228cfbcd4c9e2748`, the head of pull request #16, on which CI run 39397935800 passed both the macOS and the Linux job. Both were built from verified `git archive` exports into the bundle `ilibrary-decision-f-comparison-v4.zip` (SHA-256 `49f6001b6a69e131e2a7767691c4232efe4002cc138138a97d1c02fb128d40c8`). The comparison's preflight record shows the executable hashes `550df517…` for the reference and `a43222ca…` for the candidate, which equal the hashes measured when the bundle was built and validated offline (recorded in the ignored preparation folder `artifacts/decision-f-comparison-v4-preparation/`), and the script verifies the bundle checksums before any run; the executables that ran are therefore those of the validated bundle (measured hashes, with the checksum verification inferred from the script). The collected `doctor` output, which runs the reference executable, reports the version `0.1.0`; the candidate's version string was not collected. The executables' identity rests on the recorded commits and hashes, not on version strings or on reproducible builds.

The collected reports record macOS 27.0.1, Music 1.7, the Automation permission granted, and a media folder inside the new library `DecisionF-comparison-v4` (measured by `doctor`). The library was populated by the reference executable's `add` with 12 original synthetic tracks in 3 albums by 2 artists; the preview listed 12 planned moves, and the addition reported each album's 4 tracks as confirmed (measured). The bundle's file checks, the restoration of the synthetic dates, and the validation of 12 matched files passed (measured). The absence of a signed-in Apple Account, the disabled Sync Library, the selection of the new library in Music, and an empty library before the addition were the maintainer's visual confirmations; the collected reports do not record them, apart from the media-folder location and the comparison script's account preflight, which accepts only an empty account domain or an explicitly empty account list.

## First Attempt

The first attempt stopped at the comparison script's target-path preflight, before any `check` command ran. The collected report of that attempt therefore records the unchanged phase as `NOT RUN`. The reason was supplied separately by the maintainer from the terminal output, because the collector does not include the `compare-*.log` files to which the procedure sends the script's messages. The maintainer later observed the shell variable `MEDIA` to be empty, which plausibly explains the incorrect target argument; the value at the time of the attempt is not independently recorded. The refusal is a correct preflight outcome of the harness and not a Decision F diagnostic result.

## Second Attempt

After explicitly setting the target inside the `DecisionF-comparison-v4` media folder, the maintainer ran the comparison again. The collected follow-up report contains the complete phase results (measured). The preflight log records the passed user and account checks, the media folder, the target, and the executable hashes; the script performs its checksum, `doctor`, library-name, target, and no-overwrite checks before any run, so their passage follows from the fact that the runs occurred (inferred from the script). The six runs were made in the order reference, candidate, reference for `check --library` and then for `check PATH --library`. Every run exited with status 0, wrote nothing to standard error, and printed "Checked 12 files against the Music library", the standard note on uncompared fields and unknown cloud status, and "No problems found.". The script's summary records that both reference runs agree and that the candidate is identical to the reference in status, standard output, and standard error in both modes, with `verdict: PASS`. The redacted texts in the report are identical across the three runs of each mode; this corroborates, but does not reproduce, the script's byte-level comparison.

The recorded elapsed times were 3.320 and 3.331 seconds for the reference and 0.700 seconds for the candidate with `check --library`, and 3.316 and 3.308 seconds for the reference and 0.406 seconds for the candidate with `check PATH --library` (measured, one sequence). The second reference run, which followed the candidate, was not faster than the first, and a candidate falling back to the per-track reader would run the bulk script and then the full per-track read; the candidate's shorter times are therefore consistent with the selection of its bulk path (inferred). No instrumentation records which reader was selected, and the times include process start-up and script compilation for 12 tracks.

## Acceptance and Limits

Under Decision 49 the maintainer accepts the comparison as a limited live qualification of Decision F: on this Mac, with macOS 27.0.1 and Music 1.7, in this new synthetic library of 12 tracks, the changed commands produced observable results identical to those of the M11 reference, with stable reference runs and valid success outputs. The acceptance complements the M11 live comparison of the two readers for 12 synthetic tracks whose cloud status was `unknown`, the synthetic tests of the selection, fallback, and unknown-only guard, and CI.

The acceptance does not establish which reader the candidate selected; the cloud statuses of the tracks, which this command report does not enumerate (the M11 run observed only `unknown` in the same kind of test user); the rendering of other cloud statuses by the bulk read, which the guard sends to the per-track reader; behavior or performance with larger or personal libraries, other macOS or Music versions, or iCloud and Apple Music configurations; or anything about the removal phase, which was not run.

It does not affect the second attempt, whose report contains the complete phase results, and it is not a defect of Decision F. The collector, the comparison script, and the bundle are unchanged; any improvement belongs to a later use of the harness.
