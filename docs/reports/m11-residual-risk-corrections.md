# M11 Residual Risk Corrections

## Purpose and Status

This report records two corrections made on October 20, 2026, under the maintainer's authorization, after the independent Claude review of pull request #15 at head `b98f6b3` listed residual risks in the mount inspection and in the publication of the recovery record. The maintainer held the merge until both risks were examined against the approved safety guarantees. M11 remains accepted under Decision 45 within its recorded evidence limits; neither correction changes the qualification evidence, its source identifiers, or its recorded SHA-256 values. The implementation and tests were delegated to a subagent under a written design brief, and the coordinating agent reviewed the diff and reproduced both original failures independently. Earlier reports, including [M11 Pull Request Review Corrections](m11-review-corrections.md), are retained unchanged.

## Truncated Mount Table

The `getfsstat(2)` manual states that the buffer is filled with one structure for each mounted filesystem up to the buffer size and that the return value is the number of structures returned; it guarantees no order. `MountState.systemEntries` sized its buffer from an earlier count and accepted any positive result, so a table that grew between the two calls could silently omit entries, and an omitted backup entry yielded not mounted. The review had argued from the kernel's mount-list order that the backup could not be omitted while mounted; that order is undocumented, so the argument does not establish the guarantee. The risk is therefore confirmed from the contract.

Commit `0a55cb5` reads the table through `MountState.completeTable`, which sizes the buffer as the count plus a headroom of 8, accepts the snapshot only when fewer entries than the capacity were returned, repeats the read with doubled headroom when the buffer is full, and fails after four attempts; the failure becomes an unknown status, which never confirms a disconnection. Deterministic tests model getfsstat with a scripted table that returns the first entries up to the capacity. With the original semantics substituted in a temporary worktree, a table that grew from a count of 3 to 4 or 20 entries with the backup last was reported as not mounted, and a table that was always full was accepted (measured). With the correction, both growth cases report mounted, the larger one after a second read, an always-full table is unknown after four reads, a stable table is read once, and negative results and non-positive counts fail (measured). The disk-image integration test still observes mounting and disappearance through the real getfsstat path; the real race itself cannot be induced deterministically and is not measured.

## Replacement of an Existing Recovery Record

The `rename(2)` manual states that an existing destination is first removed. `RecoveryRecord.write` checked for an existing record, wrote a synchronized temporary file, and renamed it into place, so a record created by another actor after the check would have been replaced, contrary to the guarantee that an existing record is never overwritten. The risk is confirmed from the contract.

Commit `7eadd1b` publishes the synchronized temporary file with `link(2)`, which fails with `EEXIST` instead of replacing the destination and is available on Darwin and Linux. A refusal is reported as an existing record, removes only the temporary file, and never removes the destination; after publication the temporary name is removed, the directory is synchronized, and the record is read back and compared, with the published record removed on any later failure, as before. There is no fallback to `rename`, so a filesystem without hard links causes a refusal. An interruption between publication and removal of the temporary name leaves a complete record and a hidden temporary file, which does not weaken recovery. A regression test creates a foreign file at the record path after the temporary file is written: with the original rename-based publication, `write` succeeded and the foreign bytes were replaced (measured in a temporary worktree); with the correction, `write` refuses with an existing-record error, the foreign bytes are unchanged, and only that file remains (measured). Further tests cover a failed publication and a read-back failure after publication. The link-based publication has been measured on APFS only; its Linux behavior rests on CI.

## Verification

At `7eadd1b`, on macOS 27.0.1 (arm64) with Apple Swift 6.4, the release build succeeded, `swift format lint --strict` reported no findings, and `scripts/test.sh` passed 384 Swift tests in eight runs (measured); the Python suites and package checks are recorded in the pre-push review of this change.

## Consequences for Qualification

Both corrections add refusals or retries and change no successful path's output. A mount table that is read completely on the first attempt, which is the ordinary case when no filesystem is mounted during the read, gives the same result as before (inferred), and a workspace without an existing record publishes as before. Decision 45 continues to rest on the original qualified source; whether a separate-user observation of the corrected step 6 and step 7 is required before M12 remains the maintainer's decision.
