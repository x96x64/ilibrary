# M12 GUI-Emptiness Feasibility Procedure

## Status and Authorization

This is a prepared, unexecuted maintainer procedure for M12 (staged rebuilding, target version 0.3.0). It has not been run, and running any part of it requires the maintainer's separate authorization. It asks whether a public macOS Accessibility interface can distinguish an empty Songs view and an empty Recently Added view of Music from non-empty, loading, stale, or incompletely exposed views. It does not qualify a detector, does not change the M12 completion gate, and authorizes no registration removal or termination of Music. A preliminary check of the selected launcher's status reporting, made with harmless child processes in the maintainer's existing account and without the probe or Music, is recorded in [M12 Launcher Preliminary Qualification](reports/m12-launcher-preliminary-qualification.md); it is not a run of this procedure, and the survey itself remains unexecuted.

The procedure is performed by the maintainer in a new, separate macOS test user on a synthetic library. An agent prepares the procedure and the offline probe, assesses the resulting report, and never operates Music, the interface, or the test user.

## Existing Evidence

The M10 qualification established library emptiness through Apple Events: the guarded probe removed its own registrations one persistent ID per call and then read the library snapshot, which contained no file track (measured). The emptiness of the Songs and Recently Added views was confirmed only by the maintainer's visual observation in answer to a prompt, and the probe's report states that automatic GUI emptiness detection is not qualified. The display-order results of M10 are likewise the maintainer's visual confirmations. None of this evidence shows that an automatic detector would be reliable: a track count of zero describes the scripting model, not the presentation, and the absence of visible album cards does not show that no card exists outside the visible region.

## Detector Design Under Test

The probe `GUIProbeMac` is validation-only and never part of the product. It uses only documented public interfaces: `NSRunningApplication` to identify the one running Music process by its bundle identifier, `AXIsProcessTrustedWithOptions` with the prompt disabled to learn whether the probe is trusted, and `AXUIElementCreateApplication`, `AXUIElementSetMessagingTimeout`, `AXUIElementCopyAttributeValue`, `AXUIElementGetAttributeValueCount`, and `AXUIElementCopyAttributeValues` to read an allow-list of attributes. The messaging timeout is a setting of the probe's own element reference; it changes nothing in Music. Reading the tree can still cause Music to build or serve its accessibility hierarchy, which is an effect on the process though not on its library or settings. The probe performs no accessibility action, sets no attribute, registers no observer, sends no Apple Event, uses no System Events, takes no screenshot, launches or activates nothing, and starts no subprocess. A source test fails if any such interface appears in the probe, and a second source test fails if the probe's code, outside comments and string literals, names any accessibility function other than the trust check, the five functions listed here, and the element type identifier; both are static checks of the source, not proof of runtime behavior.

The probe needs the Accessibility permission, which the maintainer grants in System Settings in the test user; the probe never prompts, cannot grant the permission itself, and stops when it is not trusted. Granting the permission (phase 4) and revoking it (phase 9) are separate, separately authorized maintainer steps; no agent inspects, grants, or revokes it. If the principal is a terminal application, every program started from it holds the permission until it is revoked, not only the probe. Which program macOS treats as the principal of that permission, the probe binary or the terminal application that starts it, is to be determined and recorded during an authorized run, not assumed. Music's accessibility hierarchy is undocumented and may differ between versions and localizations, so every interpretation depends on a reviewed interface profile for the observed macOS version, Music version, and locale. The repository contains no profile, and none is reviewed.

Each view receives one verdict over its set of readings, and the two views are combined, the combination being candidate empty only if both views are and verified non-empty if either is:

| Outcome | Requirement |
| --- | --- |
| Verified non-empty | A complete reading of the identified view shows at least one content item |
| Candidate empty | Every preflight condition holds, the operator's separate registration count is zero, enough readings over a long enough span all show the identified view complete, not busy, not scrollable, with no content and with positive empty-state evidence (a placeholder, or a row total of zero where the profile declares the row list complete), and they agree; where the profile declares the row list complete, every reading must also report a row total of exactly zero, so a placeholder never outweighs a missing or positive total. The extractor currently never reports a view as not scrollable, so this outcome cannot arise from extracted readings |
| Indeterminate | Anything else, with every reason |

A missing node, an ambiguous or unexpected structure, an unknown label, a missing permission, a timeout, a truncated walk, a loading or unknown loading state, a possible scroll region, disagreeing readings, missing or contradicting registration evidence, a missing profile, unqualified stability parameters, or a version or locale mismatch makes the result indeterminate. No element count, missing album card, or absence of rows is sufficient alone. Unknown information is never evidence of absence: a child collection whose count is reported as no value or unsupported, a child count that is unknown at any depth including the depth limit, an enumeration whose number of children differs in either direction from an earlier count (for the application, the count of its own children before its windows are merged), an element whose role cannot be read, a negative count, and an unavailable windows list of the application each make the walk incomplete, and an incomplete walk yields neither verified non-empty nor candidate empty. Because leaf elements may report their children as unsupported, this rule may leave real Music views indeterminate even when they are empty; that would be a finding of the feasibility trial, not a reason to relax the rule, and a reviewed profile does not by itself remove it. A vertical scroll bar reported as no value, unsupported, or unreadable shows only that no scroll-bar element was returned, not that a view cannot scroll, so scrollability is either established positively by a returned scroll bar or unknown. Because no other signal of non-scrollability is used, the candidate-empty outcome is currently unreachable from extracted readings, and a feasibility trial with this probe can yield verified non-empty or indeterminate only; only a reviewed change that defines positive evidence of non-scrollability, supported by the trial, could make the outcome reachable. An element matches a rule of the profile definitely, definitely not, or possibly: an element is possible when an attribute that the rule requires, its role, subrole, identifier, or label, could not be read or was not text, and no other requirement definitely fails; the label is satisfied by either the title or the description, so a title that differs does not exclude an element whose description is unreadable. A subrole, identifier, title, or description reported as no value or unsupported is treated as definitely absent, which relies on the reader's mapping of those statuses and is to be reviewed with the trial's evidence. A view is identified only when exactly one element matches its rule definitely and no other element matches possibly, whether or not the possible element contains a container, and otherwise the reading records the view as ambiguous. A possible loading indicator is not evidence of loading, but it prevents a reading of not busy, whatever the view's own busy attribute reports, and a possible empty-state element likewise prevents a reading of no placeholder. If the interface exposes only visible or lazily created elements, the detector cannot conclude that a whole view is empty, and the result stays indeterminate. The minimum number of readings and their minimum span are inputs of the profile, at least two readings over a positive span; no value is proposed before measurement. The locale and the file-track count are supplied by the operator, not observed by the probe, so the locale check compares the operator's statement with the profile.

## Phases

Each phase below is authorized separately. The probe phases only read.

| Phase | Performed by | Changes state | Content |
| --- | --- | --- | --- |
| 1. Test user | Maintainer | Yes, a new macOS user | Create a new user whose name matches `ilibrarytest…`; do not sign in to an Apple Account; confirm in System Settings that no Apple Account is signed in and that iCloud Music Library and Sync Library are off |
| 2. Fixtures | Maintainer | Yes, Music library | In that user, create a new, empty Music library and synthetic audio from the repository's generators; never reuse an M10, M11, or Decision F library, bundle, or workspace |
| 3. Executable | Maintainer | Yes, a copy of the probe in the test user | Build the probe from the authorized commit, record the commit and the executable's SHA-256, copy the executable into the test user, and verify the same SHA-256 there before any run |
| 4. Permission | Maintainer | Yes, a privacy permission in the test user | Determine which program macOS presents as the principal of the Accessibility permission, the probe binary or the host program that starts it, from System Settings in the test user, without assuming either; grant the permission to that principal only, by hand; record which principal received it and nothing else about the settings |
| 5. Survey | Maintainer navigates manually; probe reads | Navigation only | Handle any first-launch dialogs of Music by hand beforehand, and keep the screen from sleeping or locking during each run. In the new, empty synthetic library, display Songs by hand and run `GUIProbeMac survey` with `--operator-displayed-view songs`; then display Recently Added by hand and run it again with `--operator-displayed-view recently-added` and a new output name. Do not interact with Music while a walk runs. Each run records whatever the hierarchy exposes for the interface displayed at that moment, not both views and not a verdict; the two records inform a draft profile |
| 6. Profile review | Agent and maintainer | No | Draft an interface profile from the survey for the observed versions and locale; it is reviewed before use |
| 7. Observation | Maintainer navigates; probe reads | Navigation only | For each control state, the maintainer opens the view, waits, and runs `GUIProbeMac observe` with the reviewed profile, the separately obtained registration count, and the chosen reading count and interval |
| 8. Assessment | Agent | No | Compare every outcome with the expected one and report |
| 9. Cleanup | Maintainer | Yes | Only when separately decided; revoking the permission granted in phase 4 is its own authorized step, and the test user, library, executable, records, private mappings, and any leftover temporary files are evidence until then |

The maintainer performs every view change manually; the probe never clicks, scrolls, types, selects, or navigates. The initial survey needs only the new, empty library of phase 2; a library with exactly one track, several albums, content beyond the visible region, and a loading or changing view are later control states, each prepared or navigated under its own authorization. The count of file tracks for each state is obtained by a separate, separately authorized Apple Events read of the library, whose method is fixed when this phase is authorized, and is passed to the probe; the probe itself never reads the library.

## Trust Limits

Each reading walks the accessibility tree once and extracts both views from that same walk, so a combined verdict requires both views to be identified in the same readings. When the maintainer shows one view at a time, each run yields a verdict for the view that was shown and an indeterminate combination; separately run observations are never combined by the probe and are not an atomic proof of the whole interface. A survey records whatever the hierarchy exposes for the interface displayed during its walk; it classifies nothing and cannot show which view, or that both views, were observed. Both modes check that one Music process, with the same identifier and launch date, persisted through a run: observe before each later reading and after the last one, and survey after its single walk, a survey being refused before the walk when the launch date is unknown; that does not show that the library stayed unchanged, which only the separate registration reads before and after a run can support.

The confirmations, the locale, the file-track count, the displayed view of a survey, and the source label are declarations by the operator. The output names them `operatorConfirmations`, `operatorLocale`, `operatorInventoryFileTrackCount`, `operatorDisplayedView`, and `operatorSourceLabel` and states that the probe verifies none of them; reading a hierarchy does not confirm which view the operator displayed. The executable's identity is established outside the probe: the maintainer records the commit from which it was built and its SHA-256 before the run. The freshness and origin of the file-track count are established by the separately authorized read that produces it, recorded with its time, immediately before and after the observation.

A profile cannot declare itself reviewed: it has no review field, and the probe accepts any well-formed profile whose versions, locale, and stability match. Review is therefore a step of the procedure, and the output records the SHA-256 of the exact profile bytes so that the assessment can confirm that the reviewed profile, and no other, was used. The Music version is read from the application bundle on disk, which can differ from the running process if Music was updated while it ran; the maintainer restarts Music before a run if an update is possible.

## Commands and Preflight

The probe is built with `swift build -c release --product GUIProbeMac` from the authorized source commit. Its two modes are:

```text
GUIProbeMac survey --output-directory DIR --output-name NAME.json --mapping-directory DIR \
  --time-budget SECONDS --operator-displayed-view songs|recently-added \
  --confirm-separate-test-user --confirm-synthetic-library \
  --confirm-no-apple-account --confirm-no-cloud-library [--source-commit SHA]
GUIProbeMac observe --profile PROFILE.json --locale LOCALE [--inventory-count N] --readings K \
  --interval SECONDS --output FILE --confirm-separate-test-user --confirm-synthetic-library \
  --confirm-no-apple-account --confirm-no-cloud-library [--source-commit SHA]
```

Before any accessibility call, the probe refuses when a confirmation is missing, when the process user's name in the password database does not match `^(ilibrarytest|ilibrary-test)[A-Za-z0-9_-]*$` or the user is root, or, in observe mode, when the output file exists or the profile is missing, invalid, or for another macOS version or locale. A matching user name is necessary, never sufficient: the confirmations record the maintainer's own checks in System Settings, and the probe never reads account preferences. It then checks trust without prompting and requires exactly one running Music process with a readable version; observe refuses on a Music version other than the profile's, and survey refuses when the launch date of the process is unknown. The walk is bounded by 5,000 nodes, a depth of 40, and a two-second timeout for each attribute. The locale must equal the profile's locale string exactly, and a missing `--inventory-count` makes every verdict indeterminate. If the Music process changes or disappears during observation, including during the last reading, the run stops and is recorded as stopped with the readings taken so far, and no view of a stopped run can be a candidate for emptiness.

A survey is governed by its own sequence. First, before reading anything, it resets the disposition of `SIGALRM` to the default (termination) and unblocks it, since both are inherited from the program that starts it, and arms a single-shot real-time timer (`setitimer` with `ITIMER_REAL`) for the time budget plus 60 seconds; it installs no signal handler and never signals another process. When that hard limit expires, the system terminates the probe by the signal and nothing further is written; files already published remain, and the absence of a final record is never evidence of a complete or successful walk. The operator records the actual outcome of the process as the program that started it reports it (a POSIX shell, for example, reports termination by `SIGALRM` as status 142, a value that an ordinary exit can also produce, and this form is not universal) and never infers that outcome from the files. This termination has been demonstrated only with a harmless helper program outside the repository, not with the probe. Second, a usage error, including a malformed directory, name, budget, or view, exits with status 2 and writes nothing, and a missing confirmation, a user name outside the pattern, or root exits with status 1 and writes nothing. Third, the output and mapping directories are validated: each is a path relative to the home directory that the password database gives for the process user, made only of ASCII letters, digits, and `._-`, with no hidden, empty, or traversal component and a first component other than `Applications`, `Desktop`, `Documents`, `Downloads`, `Library`, `Movies`, `Music`, `Pictures`, or `Public` in any letter case, which is refused without being opened. Each directory is then opened one component at a time from the home directory without following links; every directory on the way must be owned by the process user, writable by no one else, and contain no `.git` entry, every directory below the home directory must carry no access control list, and each final directory must also grant no access to group or others and lie on a local file system. Immediately before each publication, the held directory is checked again and its path is resolved again from the home directory, and publication is refused if it no longer leads to the same directory. The two directories must differ and neither may contain the other, and neither the record name nor the mapping name may exist yet. A property that cannot be established refuses, and a refusal at this stage exits with status 1 and writes nothing. Fourth, after this validation, a missing trust, Music process, or version, or an unknown launch date of the process, is recorded as a `refused` record in the output directory with exit status 1. Fifth, the walk runs with a time budget, checked before each element and before each element's children, and stops when it is used up or when five consecutive elements each had a request that timed out; either stop is recorded (`truncatedByDeadline`, `stoppedByRepeatedTimeouts`) and leaves the walk incomplete (`truncatedByLimit` unless a timeout ranks first), never complete. A timed-out read of an element's children is not counted toward the five when the element had already recorded another error for its children, although the walk is still incomplete. Likewise, when a scroll-bar element is read, a failure of its `AXRole` or `AXValue` request is neither recorded as an attribute error nor counted toward the five; by source review, not measurement, this affects only the recorded `scrollValue`, which no current verdict uses, while the presence of a scroll bar comes from the separately recorded request for the bar itself. Not every individual Accessibility error therefore appears in the structural evidence; scrollability that is not positively established remains unknown, and `candidateEmpty` remains unreachable from extracted readings. The budget is checked between requests, so it can be overrun by the requests of one element, about 30 seconds if each honors its two-second timeout, which has not been measured; the hard limit allows twice that. Finally, the process is read again; when there is not exactly one Music process with the same identifier and launch date, or the application element reported itself invalid, the record has status `stopped`, a stop reason, and the partial structure, and the probe exits with status 1. Otherwise the record has status `completed` and the walk's `treeStatus`, and the probe exits with status 0 only when that status is `complete` and with status 1 otherwise. Status `completed` thus means that the command ran to its end on an unchanged process, not that the hierarchy was read completely. An incomplete or stopped survey remains feasibility evidence within its stated limits, never a complete interface observation, and no survey outcome is evidence of emptiness. The time budget is required, at most 3,600 seconds, and has no default; 600 seconds is the provisional value proposed for the first survey, chosen as an engineering bound rather than measured against Music.

## Control States

The controls are synthetic and belong to the observation phase, not to the initial survey. Each is observed in Songs and in Recently Added, after the view has loaded and, where stated, while it changes.

| State | Expected outcome |
| --- | --- |
| Exactly one remaining track | Verified non-empty |
| Several albums | Verified non-empty |
| Content beyond the initially visible part of Recently Added | Not candidate empty |
| A view that is still loading or changing, for example observed immediately after a new library opens or during an addition | Indeterminate, or verified non-empty when content is shown |
| An empty library, both views loaded, registration count zero | Indeterminate, including `scrollableOrUnknown`, because the current extractor never establishes that a view cannot scroll and candidate empty is therefore unreachable from extracted readings; verified non-empty would contradict the registration count and is investigated as a discrepancy, never relabeled as empty |
| Each preflight condition missing in turn | Indeterminate with that reason |

Creating these states adds or removes synthetic content and is therefore a separately authorized fixture operation by the maintainer, outside the probe. Removing a track to reach the one-track or empty state uses the established M10 guarded method or a new library; it is never done by the probe or by a product rebuilding command.

## Evidence

An observation writes one JSON file in format `ilibrary-gui-probe-output-1`, created exclusively with owner-only permissions (mode 0600), containing the probe version, the source commit, the macOS and Music versions, the operator's confirmations, for each reading the relative time and the structural observations, and for each view and for the combination the verdict with every reason. A usage error, an existing output file, or an output location where the file cannot be created produces no file; a write that fails after the file was created can leave a partial file, which the exit status and standard error identify and which is never evidence. Observe does not restrict its output location, so its reports are placed in a dedicated owner-only directory outside any Git working tree by procedure.

A survey writes its record, in format `ilibrary-gui-probe-output-2`, into the validated output directory, and its private identifier mapping, in format `ilibrary-gui-probe-identifier-map-1` and named after the record with the suffix `.identifier-map.json`, into the validated mapping directory. Each file is first written to a temporary file named `.NAME.RUNID.partial`, created exclusively with mode 0600 and flushed to the device, then linked to its final name, which fails rather than replacing an existing file, and finally the temporary name is removed. A final name therefore exists only for a completely written file. Because the hard stop stays armed through publication, an interruption of one file leaves no file, a partial or complete temporary file without a final name, the complete file under both its final and its temporary name (after the link and before the temporary name is removed; the temporary name then does not indicate a partial file), or the complete file under its final name only. A temporary file without a final name is never a record; the probe never deletes one after a failure, and it is reviewed like other evidence, its cleanup being a separate maintainer decision. The record is published before the mapping, so a hard stop between the two, or a failure to publish the mapping (which exits with status 1 and is reported on standard error), leaves a complete record whose mapping is missing; a hard stop after both publications leaves both complete files although the probe did not end normally; and a mapping is never published without its record. The contents of each file are flushed with a full synchronization request (`F_FULLFSYNC`), falling back to an ordinary `fsync` if that request fails, which is not a verified device flush; the flush of the directory entry is attempted but its result is not checked. A final name is therefore guaranteed to denote a complete file after termination of the probe, not after a loss of power. These guarantees assume that no other process of the same user interferes: such a process could replace a temporary file between its write and its link, or move a validated directory between its final check and the link. The survey record contains the probe version, the operator's source label, confirmations, and displayed view, the macOS and Music versions, its status and any stop reason, the walk limits, the time budget, the hard limit, the elapsed time of the walk on a monotonic clock, the derived `treeStatus`, whether the application element was invalid, the truncation, deadline, timeout-breaker, unavailability, and error indications, a random `runID` shared with the mapping, and one entry for each visited element with its depth and the index, within the record, of the element through which it was reached. It records roles, subroles, child and row counts, scroll bar presence and position, and the loading attribute; it records a title or description only when it equals an allow-listed view label and otherwise records `other`; and it records an identifier only as an alias (`identifier-1`, `identifier-2`, and so on in walk order, equal for equal identifiers within the run) and a shape (`uuid`, `numeric`, `hexadecimal`, `word`, or `other`). The raw identifiers are only in the mapping, which also holds a SHA-256 in place of any identifier longer than 256 bytes. Aliases are per run, so equality between the Songs and Recently Added runs is decided by the maintainer from the two mappings. The mapping stays in the test user's custody and is never shared or given to an agent as a whole; keeping it in a separate directory is an aid to handling, not an access-control boundary, since both directories belong to the same user. At profile review, the maintainer releases only the specific identifiers that a reviewed profile needs, and no identifier is treated as public because it resembles a UUID or a hexadecimal value or because the library is synthetic. Neither mode records album or artist names, other interface text, file paths, persistent IDs, account details, positions, or screenshots, but every record is reviewed before it is shared; a stopped or refused run is recorded as such, so it cannot be mistaken for a passing observation. Standard error can contain the home path and other local details and is not shareable output.

A normal end is a process outcome that the operator has reliably identified as one of the probe's intentional exits, with status 0, 1, or 2, as opposed to termination by a signal, including the hard stop and an operator interruption, an external kill, or an unknown cause. A normal end is not a successful survey. Status 2 is a usage error and leaves no record. Status 1 is an intentional exit that can accompany, with no record, a failure to arm the hard stop, a refusal that needs no file system access, an unknown home directory, or a refused output location, and otherwise a refusal record, a stopped record, a completed record whose walk is incomplete, or a failure to publish a record or its mapping; which of these occurred is read from the files actually present and their contents, never from the status alone, and each is diagnostic evidence, not a complete structural observation. Status 0 is used only when the process identity held and the walk was complete, and even then the run counts as a complete structural observation only when the expected record exists, its `treeStatus` is `complete`, its mapping is present and matches, and the preflight conditions held. Termination by a signal is not an exit with any of these statuses, although the program that starts the probe may report it as a number (a POSIX shell, for example, reports termination by `SIGALRM` as status 142, a value that an ordinary exit can also produce), so a number alone does not show whether the process exited or was terminated. The minimum termination evidence is the operator's contemporaneous record of the outcome as reported by the starting program, together with how that program distinguishes an exit from termination by a signal, sufficient to establish which of the two occurred and, for an exit, its status. How that evidence is recorded and interpreted is defined in Recording the Process Outcome below; the method applies to the starting program and shell that the maintainer selected, whose check in the isolated test user is a prerequisite of authorizing a survey. An unknown or ambiguous outcome prevents acceptance.

A survey record is accepted as survey evidence only when all of the following hold together: the mapping named by the record's `identifierMappingName` exists in the validated mapping directory and can be read; its `runID` equals the record's `runID` and its `recordName` equals the record's file name; and the operator's termination evidence establishes a normal end as defined above, not termination by the hard-stop or another signal. A missing, mismatched, unreadable, or otherwise unverifiable mapping, or a run that ended by the signal or with an unknown outcome, leaves the evidence set incomplete, even if the record itself is complete. Three things must be kept apart: a complete walk (`treeStatus` `complete`), a complete record (a final name, which always denotes a completely written file), and an accepted evidence set (the record, its matching mapping, and a normal end). An accepted evidence set whose `treeStatus` is not `complete` remains incomplete structural evidence, and a `stopped` or `refused` record remains a stopped or refused run; neither the presence of the mapping nor a normal end changes that, and an exit status of 1 or a complete file is never by itself proof of an accepted survey. No accepted evidence set qualifies the Music hierarchy or shows that a view is empty. Accepting a sanitized record for sharing after privacy review never makes its mapping shareable: the mapping, which holds the raw identifiers, stays in the isolated test user's custody and is never shared as a whole.

## Recording the Process Outcome

The acceptance rule needs the outcome of one specific invocation of the probe. This section defines how that outcome is recorded and interpreted. It applies to the starting program that the maintainer selected, Terminal.app with a child `/bin/zsh -f`. On October 22, 2026, the status reporting of that launcher passed a preliminary check with harmless child processes in the maintainer's existing account only, recorded in [M12 Launcher Preliminary Qualification](reports/m12-launcher-preliminary-qualification.md); that check does not qualify the isolated test user, and repeating it in that user's actual environment is a prerequisite of authorizing a survey. Nothing in this section has been carried out with the probe, and it is not a ready-to-run instruction.

Six questions are kept apart. Whether the process ended by an exit of its own or was terminated or suspended by a signal is its termination. If it exited, its exit status is the number it passed to `exit`. Whether the survey succeeded depends on that status and on the record. Whether a JSON file is complete is shown by its final name, which always denotes a completely written file. Whether the walk is complete is shown by the record's `treeStatus`. Whether a record and its mapping form an accepted evidence set is decided by the acceptance rule above. No answer to one of these questions answers another; in particular, files show what a run recorded, never how its process ended.

As read from the source at commit `917b99b`, and not tested, the probe ends only through calls that exit with status 0, 1, or 2, and in a survey every exit with status 1 or 2 writes a line beginning with `GUIProbeMac:` to standard error, including a usage error, a parse error before the command is known, and the fallback on a platform without the macOS reader; an exit with status 0 writes no such line unless a temporary name remained after publication. Observe can exit with status 1 without such a line, and this section concerns surveys only. Any crash and the hard stop end the process by a signal instead. The shell reports more than the probe's own exits. Under the POSIX shell standard, a command terminated by a signal is given a status greater than 128, whose exact value is implementation-defined; a command that is not found is given 127 and one that cannot be executed 126; and an error in expansion or redirection before the command runs gives a nonzero status, often 1 or 2, without the command having run. The converse does not hold: a program can itself exit with a status greater than 128 or with 126 or 127, so none of these numbers establishes its conventional cause without a corresponding shell message, and a shell need not print a message when a command is terminated by a signal. A pipeline reports the status of its last command, every later command replaces the reported status, and a new shell starts with a status of 0. A reported status is therefore attributable to the probe only when the invocation contract below holds, and a status of 1 or 2 only when the probe's own output corroborates it.

Under the proposed contract, the selected shell is started without user startup files, or the operator records, before the run, what the command word resolves to. The verified executable is invoked by its absolute path as a single foreground simple command whose words are all literal and quoted, with no parameter, glob, tilde, or brace expansion, no pipeline, no redirection, no command substitution, no shell function, alias, or wrapper, no timing or logging utility, no other command in the same command line, and no backgrounding or suspension. No prompt hook, trap, or error-exit option is active in that shell. The operator records the process identifier of the shell (in POSIX shells, the special parameter `$$`) before the invocation and again with the status, and the two must be equal. The operator also records the shell level (`$SHLVL`) before the invocation and again after the status has been read, never between the invocation and the reading of the status, and the two must be equal. In zsh, the prompt displays the history event number (`%h`), and the status is read, as the command immediately following the invocation, together with `$HISTCMD`, which must equal the number shown in its own prompt and exceed the number shown in the invocation's prompt by exactly one; a missing, reset, unexpected, or unverifiable history number makes the outcome unknown and is never reconstructed afterwards. Equal identifiers and levels and consecutive history numbers support continuity but do not establish it with certainty; in a development measurement outside Terminal.app, a replacement of the shell by `exec` kept its process identifier and was revealed only by the reset history number and the lost prompt, and that measurement, like the other development measurements, was not archived in the repository. The terminal session must not have been restarted or replaced in between, and the status (in POSIX shells, the special parameter `$?`) must be read by that first command after the invocation, in the same shell. Standard error counts as output of the invocation only between the echo of the command and the next prompt. If any of these conditions cannot be established, the outcome is unknown.

The process-outcome record is private and stays in the test user's custody. For each invocation it states the terminal application and its version, the shell and its version, the operator's statement that every condition of the contract held, the two shell process identifiers, the two shell levels, and the history numbers of the invocation and of the status line, the SHA-256 of the executable verified immediately before the run, the start and end times, the reported status, the signal name that a shell message identified, if any, never derived from the status alone, whether a shell message reported the job as stopped, whether a shell message reported a failed lookup, execution, expansion, or redirection, without the text of any message, whether standard error of the invocation contained a line beginning with `GUIProbeMac:`, and a short statement of any deviation or doubt, which the operator reviews for paths, user names, and labels. It does not include terminal transcripts, standard error itself, the shell's messages, command history, account settings, home-directory paths, or the identifier mapping. After privacy review, the maintainer may derive from it, and give to an agent, a summary of the outcome class, the executable digest, the times, and whether every attribution condition held.

The outcome is interpreted as follows. Classifying the evidence and accepting it are separate decisions: only an exit attributed to the probe under the contract can contribute to an accepted evidence set, and every other class is rejected without asserting more about its cause than its evidence shows. A message counts as the shell's own only when it can be distinguished from the probe's standard error; when it cannot, the outcome is unknown. A shell message attributable to the invocation that names a signal is recorded as termination by that signal as the shell reported it (for example the hard stop, an interruption, an external kill, or a crash). A shell message that reports the job as stopped is recorded as a reported suspension; the signal is recorded only when the shell identifies it and is never inferred, and a stopped process has not been shown to have ended. Neither termination nor suspension is ever a normal end, and when the process is stopped or its continued existence is uncertain, its handling requires a separate decision. A shell message attributable to the invocation that reports a failed command lookup or execution, or a failed expansion or redirection, is recorded as a shell-reported invocation failure, and the probe is not credited with an exit. A status greater than 128 without a message naming a signal or reporting a stopped job, or a status of 126 or 127 without a message reporting a failed lookup or execution, is recorded as an unknown outcome, because a program can also exit with these values and the number alone establishes neither cause. Any remaining status outside 0, 1, and 2 that no shell message explains is likewise recorded as an unknown outcome. A status other than 0, 1, or 2 lies outside the documented attribution contract of the probe and is never accepted as the normal end of a survey. In each of these cases the evidence set is not accepted, even if complete files remain. Under the contract, a status of 2 is attributed to the probe's exit only when standard error of the invocation contains the probe's line beginning with `GUIProbeMac:`; it is then a usage or platform error that leaves no record and is never survey evidence. A status of 1 is attributed to the probe's exit only when standard error of the invocation contains such a line, since a failed expansion or redirection can also yield 1; the files actually present then show whether it was a refusal or a refused location with no record, a refusal record, a stopped record, a completed record whose walk is incomplete, or a failure to publish a record or mapping, each of which is diagnostic evidence only. A status of 0 is attributed to the probe's exit only when the contract, including the continuity of the shell, holds; the run is then a complete structural observation of the feasibility study only when, in addition, the expected record exists under the expected name with status `completed` and `treeStatus` `complete` and its mapping is present and matches. A status of 0 without that record leaves the run unexplained and is not accepted. Even a complete structural observation does not identify the displayed view, show that the library holds no registrations, or show that a view is empty. Without the required corroboration, or with a missing, unreadable, ambiguous, or internally inconsistent process-outcome record, the outcome is unknown, and an unknown outcome is never accepted.

Files never substitute for the process-outcome record. Because the hard stop removes nothing already published, and can fire after both publications and before the exit, a run terminated by the signal can leave a complete record, both complete files, or a complete file under both its final and its temporary name, and none of these shows a normal end. All such files, and any temporary files, remain original evidence; they are neither deleted, repaired, nor accepted because they are complete.

The status reporting of two shells was first observed offline on a development Mac, outside any test user and without the probe, with harmless child processes, and the raw results were not archived in the repository: zsh 5.9 and bash 3.2.57 reported intentional exits as 0, 1, and 2, termination by `SIGALRM` as 142 and by `SIGINT` as 130, a command not found as 127 and a file that could not be executed as 126, a failed output redirection as 1 without running the child, and the status of the last command of a pipeline. On October 22, 2026, the selected launcher, Terminal.app with a child `/bin/zsh -f`, passed a preliminary check in the maintainer's existing account with harmless child processes only, without the probe or Music, in which intentional exits with 142 and 130 were reported with the same values as termination by `SIGALRM` and `SIGINT`, termination by `SIGINT` was reported without a message, and a suspended child was resumed only after its identity had been established ([M12 Launcher Preliminary Qualification](reports/m12-launcher-preliminary-qualification.md)). That check did not qualify the isolated test user. These values describe one shell in one environment and are not universal. The check must be repeated in the isolated test user's actual environment, with harmless children and never with the probe, before a survey is authorized.

## What the Result Can Establish

A successful observation of all controls with one reviewed profile would support the detector only for that macOS version, Music version, locale, synthetic library, and timing. It would not establish compatibility with other versions, cloud-safe clearing, recovery from unknown storage states, or the correctness of any destructive stage. An indeterminate or negative result is reported as such; it is not repaired by weakening the gate. If automatic detection proves impractical, a recorded manual confirmation by second invocation can be proposed as a change of the M12 gate, which requires the maintainer's separate decision.

The other M12 prerequisites are independent of this procedure: the progress journal cannot detect the removal of a valid suffix or an older valid journal without an independent checkpoint or contradicting observation, reconciliation does not yet check files whose application is open or verified, and the first live qualification must begin with a non-destructive `rebuild prepare` phase that observes the corrected M11 disconnection and recovery-record paths.
