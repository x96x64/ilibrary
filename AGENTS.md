# iLibrary Engineering Constraints

## Project Identity and Documentation

Use `iLibrary` as the canonical product name and `ilibrary` for the executable, repository, and suitable lowercase technical identifiers. Work in this repository; do not create a nested project directory. Preserve the planning-baseline commit.

Use MLA headline-style title case permanently for all English documentation titles, section headings, and subsection headings, including README, contributor guidance, architecture documents, command references, and future documentation. Preserve literal capitalization of iLibrary, iLyrics, Apple product names, APIs, frameworks, languages, commands, filenames, options, packages, and code identifiers.

Title every GitHub release exactly `iLibrary: vX.Y.Z, Catalog-Driven Music Libraries for Apple Music on macOS`, replacing only `X.Y.Z` with the released version number (Decision 51). Use the same text as the first heading of `docs/releases/X.Y.Z.md`, in every pre-publication preview, and as the release-creation title, and verify it against this template in every release review. Do not invent a milestone-specific or feature-describing subtitle; describe new capabilities in the release body and changelog. An alternative title requires the maintainer's explicit approval before it is written or published. See [Release Titles](docs/distribution.md#release-titles).

Model the README and command-line interface on established, widely used tools such as ripgrep, fd, bat, GitHub CLI, Git, FFmpeg, and yt-dlp, and on the sibling project iLyrics. The interface is a command-based CLI with verb subcommands; do not introduce an interactive text user interface. Keep commits atomic and conventional so that history remains reviewable; perform broad cleanup through ordinary commits in a dedicated milestone.

## Evidence and Architecture

Read `docs/planning-study.md` before architectural changes. Preserve its decisions, evidence classifications, and go/no-go criteria. The study is a historical baseline, not an instruction to implement its entire roadmap. Validate architectural recommendations with working evidence, and classify findings as measured, inferred, or unknown. Never represent unmeasured Apple Music or iCloud Music Library behavior as measured fact; in particular, iLibrary documents procedures that reduce cloud matching and detects its result, but must not claim to prevent it.

Keep domain logic in Foundation-only targets (`MP4Core`, `CatalogCore`) that build and test on Linux. Confine AppKit, AudioToolbox, AVFoundation, ScriptingBridge, and Apple Events to `…Mac` targets. Do not depend on external tools such as AtomicParsley, exiftool, or FFmpeg at run time; they may be used only as independent references during verification. Do not add package dependencies without an explicit decision.

## Library Safety

iLibrary modifies user-owned music files and an Apple Music library. Every mutating command must offer `--dry-run`, must state what it will change before changing it, and must verify its result afterwards.

- Never delete an original file unless the user requests deletion and the replacement has been verified: decoded duration, codec, and, for lossless conversion, decoded PCM equality.
- Check free space before conversions. Treat truncated or partially written outputs as failures, and never count them as complete.
- Move files into the Music media folder instead of copying them, and add them album by album. Ordinary `add` must stop when the library already contains a matching track and must never remove library entries. The maintainer-approved rebuilding plan permits automatic removal only within a separately qualified `rebuild clear`, after independent backup verification, evacuation, and exact registration checks. Until M10 passes, this exception permits only the guarded M10 probe to remove its own newly generated tracks in an initially empty library in a separate test user. It does not authorize personal-library access or deletion.
- Address Music tracks by persistent ID, one operation per call. Do not rename tracks while iterating over a track collection; property changes during iteration have applied to unrelated tracks.
- Changing an album name in Music triggers automatic folder organization that can split an album across folders and break file references. Write tags to files, arrange folders, and then add or relink tracks explicitly.
- Music caches metadata independently of files. After editing files, compare the file and the library and report every difference.
- Never create a filesystem entry as a side effect of setting timestamps. A timestamp operation on a missing path must do nothing and report the path.
- Leave source files that the user did not select, such as original WAV rips, untouched.

## Scope and Rights

Do not incorporate proprietary Apple assets, private frameworks, store artwork, commercial recordings, credentials, Apple Account identifiers, or private library data. Public fixtures, examples, and tests must use original synthetic albums and generated audio. Protected audio (`.m4p`) is out of scope. iLibrary does not download audio. The software license is the Apache License, Version 2.0, decided on October 16, 2026.

## Verification and History

Test box parsing and rewriting, chunk-offset relocation, catalog matching, naming, ordering, title rules, and date handling with synthetic inputs. Validate conversions by decoding and comparing PCM, not by byte equality of encoded files. Keep generated outputs and machine-specific logs out of Git. Record sanitized hardware and toolchain context without hostnames, serial numbers, device identifiers, Apple Account details, or personal paths. Review staged changes before concise conventional commits. Review all history, ignored files, and untracked files before publication. Publish only under the repository name `ilibrary`.

Keep real purchased or downloaded files, library exports, and copyright-bearing derivatives under ignored `reference-private/`. Confirm ignore behavior before processing and audit every staged change before committing or pushing. Reference validation must report unavailable inputs explicitly; the public suite must work without private files, network access, an Apple Music subscription, or a populated Music library.

## Archival Writing

All project documentation, engineering reports, handoff records, and commit messages must use precise, restrained, grammatical, formal English suitable for an archival engineering record. Describe technical changes, evidence, uncertainty, and consequences without conversational framing, promotional language, decorative formatting, agent-centric narration, or unsupported claims. Documentation may use headings, lists, tables, and other structure where it aids the reader. Preserve completed planning and architecture reports as historical records, and record subsequent findings in new reports.

In newly authored English prose, use U+0027 for apostrophes and single quotation marks and U+0022 for double quotation marks, not typographic quotation marks. Do not alter source code, literal data, test fixtures, or historical quotations in which the exact characters are significant, and do not rewrite existing records only to change their quotation marks.

## Agent Responses

Every maintainer-facing response is written exclusively in precise, restrained, grammatical, formal English suitable for an official technical record. This applies to progress updates, technical explanations, implementation reports, reviews, pre-push reviews, change summaries, pull request descriptions, approval requests, handoff messages, completion reports, and every other authored communication, and it applies equally to coordinating agents, delegated subagents, and future sessions. Do not include translations, parallel-language explanations, or summaries in another language unless the maintainer expressly requests them, and do not add them because an earlier decision, handoff document, or instruction required them. Keep a neutral, factual, and professional tone without conversational expressions, promotional language, decorative wording, or unsupported assertions.

A response consists of continuous prose organized into appropriately separated paragraphs. It contains no headings, subheadings, standalone titles, bullet points, numbered lists, checklists, tables, decorative separators, emojis, or bold formatting; Markdown strong emphasis with double asterisks, double underscores, or any equivalent mechanism is prohibited. These prohibitions apply equally to HTML markup and to bullet characters such as U+2022, and a list must not be disguised as successive label-and-value lines or paragraphs or introduced by labels in place of prose. Italic emphasis and monospaced text are permitted, and fenced code blocks may be used where necessary for executable commands, source code, or literal technical output; these permissions must not be used to reintroduce decorative or fragmented presentation. A paragraph should ordinarily occupy at least five lines at a conventional reading width and should present related information as a complete explanation rather than as short fragments or isolated sentences. A shorter paragraph is acceptable when clarity or accurate presentation requires it. Do not insert artificial line breaks, repetition, or filler to reach a length. In newly authored prose, the quotation-mark rule of Archival Writing applies. MLA title case applies to titles and headings in documentation, which responses ordinarily do not contain.

These restrictions govern responses only. README files, plans, reports, procedures, source code, configuration, and other repository artifacts may use headings, lists, tables, bold emphasis, and conventional formatting where appropriate, and existing localized procedures, catalog content, and historical materials are not translated, reorganized, or rewritten to enforce the response format. Existing dedicated maintainer procedures such as the separate-user validation and package publication instructions may continue to be maintained in Japanese, new maintainer procedures are written in English unless the maintainer requests Japanese (Decision 43), and the generated catalog prompt retains its Japanese explanations. These materials do not permit Japanese responses.

Every substantive response is independently understandable without earlier messages. It identifies the relevant repository and branch state, the completed work, the supporting evidence and verification results, the Git identifiers, the remaining limitations, and any decision that requires the maintainer. It distinguishes measured findings, reasonable inferences, and unknowns, and it never represents incomplete verification as successful. It ends with a coherent final paragraph that states the current milestone and its verified progress and the next concrete action derived from the approved plan, the recorded decisions, and the actual repository state, and that states whether the action is already authorized or requires the maintainer. Responses do not include routine recommendations of a model or reasoning effort unless the maintainer explicitly requests them; the model and effort table in `docs/roadmap-to-stable.md` remains reference information, and model configuration needed to run an agent is unaffected.

Before sending any response, including intermediate progress messages, review the complete message against this section: it contains only English prose and permitted technical notation, its paragraphs are developed, it contains no prohibited heading, list, table, bold formatting, or decorative element, and its concluding statement is supported by the evidence and names a meaningful next action without needless repetition. Revise a noncompliant response before delivery instead of explaining the violation afterwards. A coordinating agent states these requirements when it delegates work, requires delegated reports to follow them, and reviews delegated results independently before accepting them. Decision 44 in `docs/roadmap-to-stable.md` records this policy.

In Claude Code, the project setting `.claude/settings.json` applies three controls to this section. Before generation, it selects the project output style `.claude/output-styles/ilibrary-formal-prose.md` (`outputStyle`), which adds a short reinforcement of this section to the model's instructions; it is an instruction rather than an enforcement, and it does not replace this section. During display, a MessageDisplay hook runs `scripts/hooks/response_display.py`, which, outside fenced code and inline code, replaces each run of lines that form a heading, list, checklist, table, separator, or HTML structure with one notice, withholds the second and later lines of a label-and-value or lettered sequence, and removes bold markers and emojis. It changes only the rendered text, not the transcript or what the model receives; it keeps no message text; and when it fails or exceeds its timeout the original text is displayed. After the turn, a Stop hook runs `scripts/hooks/response_format.py`, which examines the final message and blocks it once, with a corrective reason, when it contains a Markdown heading, a list or checklist item, a table, bold emphasis, a decorative separator, an emoji, a standalone title, or an unterminated code fence outside fenced code and inline code. It also rejects HTML table, list, heading, bold, and rule tags, lines that begin with a bullet glyph, and two or more successive lines or short paragraphs that begin with a label and a colon or with a lettered enumerator. A response that still violates the format after its one correction is reported to the maintainer and not blocked again.

These controls have measured limits, recorded in `docs/agent-handoff.md`. With the engine flag `--include-partial-messages`, which the Desktop application uses, the original text streams as partial output before the display hook's replacement reaches the completed message, so the display hook cannot prevent prohibited text from appearing while it streams. Neither hook judges language, tone, paragraph development, or the concluding paragraph, and neither inspects text that the application displays from tool calls, delegated-agent reports, or sessions of other agents such as Codex; the Stop hook also does not inspect intermediate messages. The hooks supplement the review required above and do not replace it. Their tests run with `cd scripts/hooks && PYTHONDONTWRITEBYTECODE=1 python3 -m unittest test_response_display test_response_format`.

## Commits

Follow [Conventional Commits](https://www.conventionalcommits.org/) as in iLyrics: `type(scope): subject`, with a lowercase, imperative, specific subject without a trailing period, intelligible independently of the development conversation. Use a body only to record rationale and consequences. Keep the human author and committer identities.

## Commit Attribution

When Codex materially contributes to a commit, append `Co-authored-by: Codex <codex@openai.com>` after a blank line in the commit message. When Claude materially contributes, append `Co-Authored-By: Claude <noreply@anthropic.com>` under the same conditions; a model-specific display name such as `Claude Opus 5.5` may precede the address. Include both trailers when both agents contributed materially. Apply these trailers only when the contribution is supported by the work performed; do not add them to unrelated or unassisted commits, and do not create artificial commits to influence contributor statistics. Follow GitHub's [co-author trailer format](https://docs.github.com/en/pull-requests/how-tos/commit-changes/creating-a-commit-with-multiple-authors).

Historical attribution changes require explicit approval, a verified recoverable backup, preservation of original authors, committers, dates, messages, change sequence, and repository contents except for the approved attribution metadata, and an explicitly approved lease-protected remote update.

## Agent Handoff

This file governs Claude Code, Codex, and other agents equally, including subagents to which work is delegated; `CLAUDE.md` imports it. A coordinating agent that delegates work states its objective, permitted changes, constraints, and verification criteria, and reviews the actual changes and evidence before accepting them. Keep project state in the repository rather than in conversations: at the end of each milestone, update the Current Status of `docs/roadmap-to-stable.md` and commit it, so that any agent can resume from the repository alone. Cloud sessions run on Linux and can build and test only the Foundation-only targets; verify macOS-only changes through macOS CI or on the maintainer's Mac. Releases, tags, repository creation, pushes, and publication require the maintainer's explicit approval in the current conversation. Before each push, present in English a preview of the changed documentation, a summary of the principal changes, the verification results, the privacy check, and the applicable approval.

Continue within the scope already authorized in the active conversation without requesting repeated confirmation. When a new decision is necessary, explain it in plain, formal English, describing the alternatives and a recommendation in prose. Preserve restrictions on personal-library operations even during autonomous work.
